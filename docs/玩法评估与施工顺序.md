# 玩法评估与施工顺序

> 评估对象：`docs/系统说明.md`（昼夜季节 / 成就藏品 / 商店交易 / 升级自动化 + 5 项拓展）
> 评估基线：当前仓库代码（src/*.js，存档 v9，4 场景 × 3 订单 + 练习订单）
> 结论口径：可行性 = 现有代码能复用到什么程度；可玩性 = 对核心循环（塑形 → 雕刻 → 上色 → 守窑 → 交付）的增量，不是"功能多不多"。

---

## 0 结论速览

| 玩法 | 可行性 | 可玩性 | 成本 | 建议 |
|---|---|---|---|---|
| 相机模式 + 一键截图 | 高（world.js 已有轨道相机） | 中（传播向） | 0.5 天 | **先做**，性价比最高 |
| 图鉴系统 | 高（`createBowlPreview` 可直接复用） | 中高 | 2-3 天 | **先做**，把 4 件藏品变成可阅读内容 |
| 商店与交易 | 高（升级经济已在跑，只缺货架） | 高（给钱一个出口） | 3-5 天 | **先做**，但只卖消耗品/增益 |
| 窑变与稀有度 | 高（复用鼓风小游戏） | 高（重复利用已做内容） | 3-4 天 | 做，第二次烧制是廉价的"再来一轮" |
| 每日挑战 / 熟客 / 预订 | 高（订单参数化即可） | 高（长线留存） | 2-3 天 | 做，但依赖全局时钟 |
| 昼夜与季节 | 中（灯光/曝光可复用，缺时钟） | 中（氛围向，机制薄） | 3-5 天 | 做，作为时钟的第一批消费者 |
| 成就 + 熟练度 + 称号 | 中（缺事件钩子，缺 UI） | 中高 | 4-6 天 | 做，但必须等事件钩子落地 |
| 技能树（熟练度分支） | 低（纯新增 UI + 数值重调） | 中 | 5-8 天 | **延后**，先只做线性熟练度 |
| 自动化 / 学徒 | 中低（会改写核心循环） | 风险项 | 8-12 天 | **最后做**，且只自动化非技巧步骤 |
| 文物修复 / 考古 | 低（全新玩法） | 未知 | 10 天+ | **先做原型再立项**，不要先进排期 |

一句话总结：**先把共享底座（事件钩子 + 全局时钟 + 存档迁移）做掉，再按"复用度从高到低"铺功能；自动化与考古放最后，因为它们要么改核心循环，要么是全新玩法。**

## 2 逐系统评估

### 2.1 昼夜与季节 —— 可行性中 / 可玩性中

- **机制现状**：没有任何游戏时钟。`clockPolicy`（`src/workshop.js`）只服务"效率计时"和"守窑暂停"，在失焦/切页时暂停——**别把这个语义和昼夜混用**。
- **最小可用版本**：一个 `GameClock`（累计秒数 → 时辰序号 / 天数 / 季节），只做三件事：① 驱动 `world.js` 的 hemisphere + sun 色温与强度、`toneMappingExposure`；② 驱动 `SCENES[].light/wall/floor/sun` 的插值；③ 提供一个 `buffs` 只读表给结算乘数。
- **坑**：
  - 20 分钟 = 1 天 → 一单（≤5 分钟效率奖）约占 1/4 天。若按"每天给一次 buff"，buff 的节奏会非常快，数值要给得很轻。
  - 时钟必须自己累计 dt（跟随 `main.js` frame 的 dt，且已有关闭页暂停），否则玩家挂机一晚回来跳 30 个季节。
  - 季节"视觉为主"是对的：不要给季节做硬性失败条件，只做 ±5% 级别的收益浮动。
- **可玩性判断**：纯氛围，不会让玩家多玩一单。价值在于"每次回来场景不一样"，属于**留存装饰**，不该排在前面。

### 2.2 成就 + 熟练度 + 称号 —— 可行性中 / 可玩性中高

- **成就**：40 条左右、外部 JSON 管理是正确方向。最低成本形态：
  ```
  {id, title, desc, trigger:'submit'|'upgrade'|'collect'|'kiln'|'practice', when:{minScore:95, scene:'kiln-flame'}, reward:{coins:200}}
  ```
  代码侧只需要 6 个触发器 + 一个 handler 表，条目全部是数据。**没有事件钩子之前不要开工**，否则 40 条判定会散在主线里。
- **熟练度/称号**：熟练度 = 一个累计整数（通关 + 分数 + 收藏）+ 阈值表 → 称号。这是**一天级别**的活。技能树才是大头（新面板 + 每级数值 + 免费重置的存档语义）。
- **可玩性判断**：成就是"给探索过的机制补一次奖励"，和现有练习订单天然互补；但成就不改变任何一次操作的手感，它是**收集向留存**，不是玩法。
- **建议**：先做成就 + 线性熟练度；技能树等熟练度跑一版、看过玩家点法再决定要不要。

### 2.3 商店与交易 —— 可行性高 / 可玩性高

- **现状**：只有一个货币出口——贴画 400 币（`campaign.js` `DECAL_PRICE`），且每场景限一次。钱在中后期是纯堆着，这是当前**最大的经济空洞**。
- **最小可用版本**：一个货架数据表（复用 `WORKBENCHES` 的结构）+ 现有的 `upgradeStation` 扣钱逻辑 + 三个品类：
  1. **增益**（一次性/限时）——直接喂给 `orderIncome` 的乘数，代码量最小；
  2. **陶土原料**（解锁制，改变 `suppliedClay` 的起始接近度）——已有 level 1-3 的现成梯度，加一档即可；
  3. **外观**（工作台皮肤）——**最贵**，要建模/换材质，建议最后做。
- **买办 / 神秘商人**：都是"同一货架 + 不同商品池 + 随机种子"，不要写成两套系统。神秘商人 = 每日刷新的高价池（依赖时钟）。
- **可玩性判断**：高。它把"重复三单"变成"攒钱换效率"，是自动化的前置经济基础。
- **坑**：价格随熟练度浮动会引入"读不懂的定价"。第一版建议固定价 + 明确折扣标签。

### 2.4 升级与自动化 —— 可行性中低 / 风险最高

- **现状**：升级已经覆盖 6 个工作台（每台 3 级），"学徒自动化"是它的自然延伸，但：
- **核心矛盾**：本作的技巧全在手上（推泥对称、刻刀容错、镜像上色、守窑带）。**任何"自动完成"都是在自动通关**。全自动生产一件 80 分以上的作品，等于删掉游戏。
- **可接受的最小形态**：
  - 只自动化**非技巧步骤**：取泥、鼓风保持（把火候稳在带内但不保证完美）、大面积铺底色；
  - 学徒产出必须有**质量上限**（例如最高 75 分，永远拿不到 80 的首通与效率奖）；
  - 学徒是"时间队列 + 离线结算"，需要存档时间戳与"关页也算时间"的明确规则。
- **可玩性判断**：如果做成质量上限 + 慢速，它是合理的"挂机产出"；如果做成无上限，玩家第一天就会用它跳过全部塑形，游戏寿命立刻结束。**这个项目里最需要数值护栏的系统。**
- **建议**：等商店/稀有度把经济跑顺、核心循环确认不需再调之后再做。否则数值要重调两次。

### 2.5 相机模式 + 一键截图 —— 可行性高 / 可玩性中

- **现状**：`world.js` 已有轨道相机（`orbit.azimuth/polar/radius` + `placeCamera()`），第一/第三人称与鸟瞰只是给这几个参数加目标值和缓动。
- **成本**：0.5 天。截图模式（隐藏 UI + 截图按钮）更便宜：给 `#app` 加一个 class，用 `renderer.domElement.toDataURL` 即可（`canvas` 需要 `preserveDrawingBuffer`，注意 `world.js` 目前没开这个参数，截图要么在 draw 后同步取，要么加参数）。
- **可玩性判断**：不增加玩法，但**传播价值最高**——这是给小红书/社媒准备的。投入产出比第一。

### 2.6 图鉴系统 —— 可行性高 / 可玩性中高

- **现状**：`collection`（4 件）+ `createBowlPreview` 已能展示成品；缺的是"详情页 + 文案 + 解锁奖励"。
- **成本**：2-3 天（其中一半是写介绍文案）。
- **建议**：图鉴条目直接复用 `SCENES` 的 `reference/description` 字段扩展，**不要**新建一套"文物数据库"——除非真要做 40+ 件文物（那时候才需要独立 JSON）。
- **坑**：`collection` 只有 4 件，图鉴页会显得很空。图鉴的体量取决于内容量，不取决于系统；**先把"每场景 5 个预设"扩到 15 个，图鉴才立得住**（见 §3 内容吞吐）。

### 2.7 每日挑战 / 熟客 / 预订 —— 可行性高 / 可玩性高

- **现状**：订单本来就是"预设 id"（`PRESETS[level]`），参数化成本低。
- **最小可用版本**：
  - 每日挑战 = 日期做种子 → 选一个预设 + 难度系数（目标更窄/窑带更紧/时间更短）+ 一次性的熟练度奖励；
  - 预订 = 一个带截止时间的多单任务（必须有时钟，和 §2.1 一起做）；
  - 熟客 = 同一顾客连续订单，条件更严但报价更高。
- **可玩性判断**：高，因为**它复用已有内容**（同一个预设换参数），是"用最少新内容换最多新局"的典型。
- **坑**：截止时间要用游戏内时间，不要用现实时间（手机玩家会被罚）。

### 2.8 窑变与稀有度 —— 可行性高 / 可玩性高

- **现状**：鼓风小游戏已经是通用件（`createFireDrift`/`fireGrade`/`fireBand`），窑变 = 第二次烧制 + 更窄的带 + 稀有度表。
- **最小可用版本**：交付后可"另烧一次"，产出 `rarity`（普通/精品/传世）→ 直接乘进售价；稀有位给一件展示品（`shelf` 已有 0-9 的槽位）。
- **坑**：窑变会覆盖成品，必须**另存**（`piece.pixels` 已经是 Uint8Array，拷贝一份即可），否则玩家点错就毁一件作品。
- **可玩性判断**：高。它是"重复利用已经做完的内容"，也是当前唯一能把"80 分合格"和"95 分追求"分开的机制。

### 2.9 文物修复 / 考古 —— 可行性低 / 先做原型

- **现状**：零基础。
- **判断**："碎片拼合 + 倒计时搜寻 + 商店碎片"是三套机制叠在一起，成本 10 天起，且与核心循环无关（它不改变塑形/上色的手感）。
- **建议**：只做一个**独立原型**（1 天：把一件藏品的像素图随机打碎成 6-9 块，让玩家拖回原位），验证手感后再决定是否进主线。**不要先进排期。**

## 3 横切风险（比单个玩法更致命）

1. **内容吞吐是第一瓶颈，不是系统。**
   `targetPixel`（`src/sculpture.js` 29-48 行）是**每个设计手写一段形状函数**，5 个预设 = 5 段代码。成就 40 条是数据，设计 40 个也是数据——但后者现在要写 40 段几何代码。
   → **在做任何"需要更多内容"的系统（图鉴、商店外观、每日挑战）之前，先把设计改成数据驱动**：`{shapes:[{type:'ellipse',cx,cy,rx,ry,color}], bands:[{y0,y1,color}]}`，一个解释器吃掉全部设计。这是**一次投入、长期复利**。

2. **只有 2 种颜色。**
   `PALETTE = [null, 瓷白, 钴蓝]`。粉彩/青花釉里红/描金都要加色。好消息：`compareSculpture` 的上色分已经按颜色类循环，加色**不用改评分**；坏消息：每个设计的颜色区域仍是手写。→ 和上一条合并解决。

3. **存档严格校验。**
   `restoreV9` 任何字段不合法就 `return fresh()`（整档清零）。新增字段必须**可选读取**（缺失时给默认值），并且每加一个系统就 bump 一次版本 + 写一条迁移。建议顺手加一个"存档体检"：把非法原因写进 console，否则线上丢档无从排查。

4. **i18n 是乘法器。**
   每个新按钮/标题/描述 = 中文 + 英文各一条（`src/i18n.js` 681 行）。40 条成就 = 80 条文案。排期时**把文案时间算进功能时间**。

5. **渲染开销。**
   现有 5+ 个独立 `THREE.WebGLRenderer`（世界、首页轮播、瓷碗预览、工作台预览、窑炉）。任何"再来一个 3D 面板"（图鉴详情、技能树预览）都应**复用已有预览器**而不是新开一个 WebGL 上下文。

6. **数值护栏。**
   目前一单收益 80-248 币，贴画 400，升级 100/200。加自动化/商店/稀有度后**货币通胀几乎是必然**。建议在商店上线时把"每场景只能升 3 级"改成"总额度"，否则后期钱无处可花。

## 4 施工顺序

排序原则：**共享底座 > 复用度高的功能 > 吃内容的功能 > 改核心循环的功能 > 全新玩法**。

### P0 底座（3-4 天，做完之前不要开新玩法）
1. **事件钩子**：`submit / upgrade / collectClay / fire / practice / dayChange` 六个触发点，统一派发。
2. **全局时钟**：累计 dt、暂停语义、时辰/天/季节换算；存档只存"累计秒 + 起始日期"。
3. **存档 v10**：可选字段读取 + 迁移函数 + 非法原因日志。
4. **设计数据化**：`targetPixel` 改成数据解释器（先迁移现有 5 个设计做验证）。
> 验收：`npm test` 全绿；旧 v9 存档能读进来；5 个设计产物与改造前**逐像素相同**。

### P1 立竿见影（5-7 天）
5. **相机模式 + 截图**（0.5 天）
6. **图鉴**（复用 `createBowlPreview`）：先把每场景预设从 5 扩到 8-10 个，图鉴才有内容
7. **商店货架**（只卖增益 + 原料）：给钱一个出口
> 验收：不新增 WebGL 上下文；商店能把钱花出去；图鉴能点开每件藏品。

### P2 留量（7-10 天）
8. **昼夜与季节**（消费时钟；只做光色/曝光 + 轻 buff）
9. **窑变与稀有度**（复用鼓风；必须另存成品）
10. **每日挑战**（日期种子 + 参数化预设；复用窑变/稀有度做奖励）
> 验收：一天内能玩到 2 种不同参数的订单；窑变不会毁掉成品。

### P3 收集向（6-8 天）
11. **成就**（JSON 表 + 6 个触发器）
12. **熟练度 + 称号**（线性阈值，不做技能树）
13. （可选）**技能树**——只在熟练度跑过一版、确认玩家有点法偏好后做
> 验收：40 条成就全部来自 JSON，零硬编码判定。

### P4 自动化（8-12 天，最后做）
14. **学徒队列**（时间制、离线结算、质量上限 75 分）
15. **学徒训练**（用高难度挑战"示教"提升效率，而不是直接卖等级）
> 验收：自动化产出的作品永远拿不到 80 分首通与效率奖；关页重进队列时间正确。

### 单独立项
16. **文物修复原型**（1 天验证手感，通过才排期）

## 5 明确建议

- **不做**：站内"季节切换"做成独立按钮矩阵。季节跟着游玩推进自动走即可，按钮只会增加 UI 负担。
- **先不做**：技能树、外观商店、文物修复主线。
- **必须做在前面**：事件钩子、全局时钟、设计数据化——这三件事任何一个晚做，后面每个系统都要多改一遍主线。
- **数值上唯一不能妥协的**：自动化不得产出 80 分以上作品。
